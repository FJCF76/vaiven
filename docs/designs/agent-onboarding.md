# Design: agent onboarding — the manual has two audiences and never says which you are

## Problem Statement

A third-party AI agent was told to read `vaiven.owncompute.com` and try the product. It
praised the manual as genuinely self-contained, reached §1, and hit:

> ask the user to run `vaiven tenant create "<their name>"`

It found no `vaiven` binary, no published source for one, probed six plausible install paths
(all 404) and stopped. That was the correct call: without a tenant key `POST /api/docs` can
only return 401.

Second blocker: the documented setup writes to `~/.claude/skills/vaiven/SKILL.md`, which its
sandbox refused three ways. Because the manual implies installing is a prerequisite, it
concluded it was stuck.

This is not new work. `TODOS.md:15` already carries a P0 — *"The cold-surface test on
`guide.md`. A fresh agent, one URL, nothing installed. Every retry is a guide bug."* That
report **is** the cold-surface test, run for real by someone who is not the author. It failed.

## What makes this worth getting right

The manual is read by machines. A human skims past an ambiguity; an agent stops at it and
reports back. That makes the manual the most testable artifact in the product — and this
report is the test result.

## Premises (all measured, agreed 2026-08-19)

1. The product is **already fully remote-capable**: a caller with only a tenant key can
   create documents, mint per-person keys, list and revoke them, republish, list and delete,
   all over HTTPS. Verified live.
2. **Exactly one operation needs the server box**: creating the tenant. `src/cli.ts:13` opens
   SQLite directly and has no network client; no `/api` route mints tenants.
3. The root cause is the unresolved design question at `docs/designs/vaiven-v1.md:950`,
   *"Self-hostable by others, or one instance?"*, now decided: one operator-provisioned
   instance, self-hosting by cloning.
4. **No new capability is required.** The fix is framing.
5. No new artifact ships, so no distribution or CI work. The CLI stays server-local and
   unpublished (`package.json` is `private: true` with no `bin` entry).

## The diagnosis

The manual has **two audiences and never distinguishes them.** §1 reads correctly to the
operator, who has a shell on the box, and is a dead end for the agent, who does not. Every
other symptom follows from that one omission.

Found while checking it: the dead end is **also in the runtime**. Five places in the live API
tell a keyless caller to run `vaiven tenant create`, including the 401 body — the first thing
a cold agent meets, before it reads any documentation:

```
src/routes/api.ts:95, 115, 132, 218   "A tenant key comes from `vaiven tenant create`"
```

## Cross-Model Perspective (Codex, gpt-5.6-sol)

Contributed the structural fix: a **role gate** as the first substantive text, naming the two
audiences and telling each what to do. Also: label every CLI command "run on the Vaiven server
host", make the agent HTTPS path §1, move operator provisioning later, add a first-success
probe, and state the trust model — tenant keys are operator-issued bearer capabilities and
must never be published into document content. That last one is a real leak path here, since
the agent authors the HTML.

**Its challenge to premise 4, recorded rather than dismissed:** documentation can explain a
missing credential but cannot let a cold agent *complete* a trial. Evidence that would prove
it right: repeated black-box runs where agents follow the revised guide correctly and still
stop for want of a key. That is exactly the cold-surface P0, and it is now the falsification
test for this decision.

## Approaches Considered

- **A — manual-only patch.** Key-first prose, corrected CLI references, install marked
  optional. Rejected: leaves both the two-audience confusion and all five runtime hints.
- **B — role gate restructure.** Fixes the manual properly. Rejected: an agent that probes the
  API before reading, which is what a cold agent naturally does, still gets sent to the CLI.

## Recommended Approach (REVISED after /autoplan CEO review, 2026-08-19)

**Approach C was approved, then cut.** Both CEO voices agreed 6/6 that it served an audience
the kill criterion does not count. Ship the hygiene fix; freeze the rest.

### In scope

1. **The five runtime hints** — `src/routes/api.ts:95,115,132,218` tell a caller to run
   `vaiven tenant create`, a binary that has never been published. This is the 401 body a cold
   agent meets *before* reading anything. It is a correctness bug, not polish.
2. **The trust-model line** — the agent authors the HTML, so publishing its tenant key into
   `content` is a live leak path. One sentence closes it.
3. **One corrected line in `guide.md` §1** — where the key comes from, and that only the
   operator can issue it.
4. Judgment call, flagged: the same defect in `guide/errors.md` and `guide/limits.md`, which
   also name CLI commands at a reader who cannot run them. Identical class, one line each.

### Frozen until a non-author human has used a document

Role gate, section reordering, first-success probe, optional-save prose, new regression guards.

### Errors in the first draft of this document, corrected

- **The falsification test could not return false.** Success was "completes a round-trip OR
  stops naming what it needs". Under operator-provisioned tenancy no cold agent can take the
  first branch, so the second always fires and the test passes by construction.
- **Premise 4 was false inside its own plan.** "No new capability is required" sat alongside
  two items that change runtime behaviour. Struck.
- **It closed a P0 it never exercised.** `TODOS.md:15` is a **read-back** test — hand the agent
  a `/r/` URL and require the `guide` field alone to bootstrap it. The third-party report was
  an **authoring** test against the bare homepage. The two are not the same and the P0 stays
  open.

### The strategic decision that must not ride in on this branch

`docs/designs/vaiven-v1.md:950` ("self-hostable by others, or one instance?") was being resolved
inside a documentation change. It is extracted. Note for whoever takes it up: **"self-hosting by
cloning" makes adoption unobservable, and the kill criterion is a count** — if usage cannot be
counted the criterion can never fire, and the project neither succeeds nor stops.

### Alternatives never costed, recorded for that decision

- **D — invite-gated `POST /api/tenants`.** Removes the sole server-local operation entirely.
- **E — a public demo tenant**, short expiry, tiny quota, no read keys. A cold agent completes a
  real round-trip in one call. Called the 10x reframe; the sandbox host, CSP and quota machinery
  that makes it safe is already built.
- **F — publish the CLI.** Dismissed by a premise that stated a conclusion as a constraint.
- **G — do nothing here; run the human gate.**

## Success criteria (replaced)

Not "the agent fails politely". The only numbers that count: **tenant keys issued to non-author
humans**, and **documents those humans edited**. Today both are zero.

## The assignment

Two experiments, both cheap, both unrun:

1. **The read-back cold-surface test** (`TODOS.md:15`). Hand a fresh agent one `/r/` URL and
   nothing else. It must say what the document is, what changed and who changed it. No key
   needed. Ten minutes.
2. **The Phase 4 human gate.** Hand the write URL to someone who has never seen the system, with
   no explanation. They must state unprompted what the document is, that their changes saved,
   and that their edits are recorded under a name.
